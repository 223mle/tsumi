# html-explainer

読み手が一度読めば仕組み・差・判断を理解できるHTMLを作る。本文は[unslop](../unslop/SKILL.md)、図とページは同梱の部品に任せる。モデルは内容・値・関係をJSONで渡し、座標・配色・アニメーション・アクセシビリティは部品が決める。

## 読み手の問いから構成を決める

1. unslopを読み、読み手がこの資料で答えを得たい問いを1〜3個決める。unslopの文書の種類は「解説」を基本にし、操作手順が主なら手順書として書く。提供資料を事実の起点にし、数値の単位・条件・時点・確度を保つ。推測を実測に変えない。未測定の工程は秒数を仮置きせず `unknown: true` で描く。
2. 最初の画面で答えを見せる。`takeaways` に結論を2〜4文で書き、見出しは「設定」ではなく「ヒットするとデータベースへの経路が消える」のように節の要点で書く。
3. 1つの図には1つの主張だけを持たせる。図のタイトルは対象、本文は読み取り方、captionは条件・出典・未確認事項に使い、同じ一文を3か所に書かない。
4. 初出の専門語は `glossary` に定義し、本文で `[[用語]]` と書く。ホバー・フォーカス・タップで定義が出る。図のノード名が用語と同じなら、用語にカーソルを当てたときに図の該当部分も光る。
5. 詳しい理由や例外は `details` に畳み、本筋を短く保つ。段落は1〜3文、1段落に1つの話題にする。

## 図を選び、動きは理解を助けるときだけ使う

[図の選び方](references/figure-selection.md)で、問いに合う部品を選ぶ。主な対応は次のとおり。

| 読み手の問い | 部品 | 動き |
| --- | --- | --- |
| 誰が誰に、どの順で何を送るか | `sequence`（`mode: "steps"`） | 1メッセージずつ進める。未来の手順は薄く見せ、全体と現在地を同時に示す |
| 何がどこを通るか、前後で経路がどう変わるか | `network` | 同じ配置のまま前後を補間する。`notes` で状態ごとに1文を出し、`marks` で起きる場所に札を付ける。`motion: true` で番号順に流れる点を再生できる |
| 構造や履歴の形がどう変わるか、どこでぶつかるか | `network` の比較。まだないノードは `hidden_nodes`、衝突は `kind: "conflict"` | 同じ配置のまま前後を補間する |
| どこで時間がかかり、何が重なるか | `timeline` | 前後で同じ軸のまま棒が動く。timelineのspecに `baseline: true` を書くと元の状態を点線で残し、減った分を見せる |
| ある量につれて別の量がどう変わるか、どこで逆転するか | `line`。交点を `points` で示す | 静止。比較やスライダーにもできる |
| どの量で上限を超えるか | `threshold` | 静止 |
| ある量を変えると結果がどう変わるか | `timeline` などを `mode: "slider"` にし、値ごとのvariantを並べる | 読み手がつまみを動かし、値の間を補間する |
| 何が大きく変わるか | `stats` ブロック | 静止。2〜4個の数値を大きく見せる |
| どちらを選ぶか | `compare` ブロック、または `decision` | 静止 |
| 処理や問い合わせがどの順に進むか | `network` の辺に `step` 番号を付け、`mode: "steps"` にする | 1段階ずつ進め、各段階の説明文を同期する |

動きは、順序・因果・前後の差を示すためだけに使う。読み手が自分で進める操作を基本にし、自動再生は「自動で進める」ボタンを押したときだけ行う。装飾的なループ、スクロール連動の演出、パララックスは使わない。reduced-motion・印刷・JS無効のときは、最終状態と全手順の文章を静止表示する。

スマートフォンの読み手が多い資料では、`network` のノードをグリッドの2行（`row` が2種類）以内、`sequence` の参加者を5人以内に収める。この範囲なら、幅600px以下で縦向き・列を詰めた配置へ自動で切り替わり、横スクロールなしで全体が読める。3行の `network` も、隣り合う行を結ぶ辺のラベルが短ければ縦向きになる。`timeline`・`threshold`・`line` も切り替わる。切り替えられない図は `render.py` が `render: note:` で理由を示すので、配置かラベルを直す。

1つの図で対象を区別する色は `blue`・`amber`・`teal` の3色までにする。色だけで区別せず、ラベル・線種・札を併用する。

複雑な図を標準の `flow` や表へ押し込まない。部品で表せない関係だけ[特殊なSVG](references/figure-selection.md)の手順へ進む。

## 文書JSONから生成する

[文書の入力](references/input.md)と[作例](assets/showcase.json)を読み、文書JSONを書く。図は `blocks` の `diagram` に[図の入力](references/diagram-input.md)のbundleを入れる。スキルのディレクトリから実行する。

```sh
python3 scripts/render.py document.json --output document.html
```

入らないラベル、衝突する経路、長すぎる説明は生成時に拒否される。拒否されたら、ラベルを短くして詳細を本文やステップの説明文へ移すか、ノードの配置を変える。文字を小さくする、検査を外す、生のHTMLやSVGを混ぜることで回避しない。

単独の図だけを作るときは `scripts/diagrams.py figure.json --output figure.html` を使う。`--fragment` を付けると既存ページへ埋め込むfigure断片になり、そのページには `assets/diagrams.css` と `assets/diagrams.js` を一度だけインラインで組み込む。

### 元のHTMLと同じ内容で作り直す

元HTMLの全figureに対応するbundleを、順番に `{"figures": [...]}` へ並べる。次のコマンドが本文・見出し・表・出典を保ち、全図とページのテーマを置き換える。元のSVG座標、CSS、JSは再利用しない。図からしか値を取得できない場合は、描画位置から読み取った概数であることをcaptionに記す。

```sh
python3 scripts/compose.py source.html figures.json --output rebuilt.html
```

元資料は変更しない。元図の数とbundle数が違えば生成は失敗する。参照HTMLがある場合は、作成前に主要な図のスクリーンショットを確認し、色が表す対象、共通の軸、グループ、境界、前後切替の役割を拾う。本文や図の数を減らしてコンパクトに見せない。

## 初稿を実物で検証する

納品前に次を行う。検査が通っても、意味の正しさと読みやすさは保証されない。

- 原資料と主体・条件・例外・数値・時点・確度・出典を照合する。資料にない規則（承認の順番など）を図のために仮定したら、captionに「想定」と書き、本文の未確定事項にも挙げる。
- `render.py` に `--text-out prose.txt` を付けて本文を取り出し、unslopの `find-ambiguous.py` を `prose.txt` にかける。
- 2つの検査を実行し、スクリーンショットを実際に開く。

  ```sh
  node scripts/check-render.cjs document.html render-evidence
  node scripts/check-diagrams.cjs document.html diagram-evidence
  ```

  PlaywrightとChromiumを使う。必要なら `NODE_PATH` と `CHROME_PATH` を指定する。
- [図と本文を食い違わせない](references/figure-selection.md#図と本文を食い違わせない)の項目を、全ステップ・全variantのスクリーンショットで確かめる。
- 画像を見て、次の3点を確かめる。最初の画面で題と要点が読めるか。各図が1つの主張を示し、矢印の向きと動詞からラベルの所属が分かるか。390px幅で、図の今の段階や変わった部分が見えるか（横スクロールは自動で追従し、読み手は「全体を縮小表示」も使える）。
- 元資料があるときは、同じ幅・同じ表示状態で図とページの高さを比べる。本文や注釈の削除、フォント縮小で帳尻を合わせない。

[確認項目](references/verification.md)に、自動検査で分かることと分からないことを記載している。

修正が必要なら、同じ不備を防げる共通部品を先に直し、同じJSONから再生成する。納品HTMLだけへの座標・色の手直しは、次の生成へ改善が残らない。個別編集をした場合は、その事実を報告する。

完成したHTMLを開いてリンクを返す。比較を依頼された場合は、改善した点だけでなく元資料に劣る点、初稿からの修正、未確認を短く伝える。

[参照スキルと採否](references/sources.md)は、このスキルの設計変更時だけ参照する。
