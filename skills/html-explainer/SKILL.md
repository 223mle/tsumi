# html-explainer

読み手が「何が起きるか」「なぜそうなるか」「何を選ぶか」を図と日本語で理解できるHTMLを作る。既定は、明るい紙面、左の目次、結論から始まる節、意味ごとの配色、根拠を添えた図。装飾の多いダッシュボードにはしない。ユーザーの既存デザインや明示した形式があれば優先する。

## 入力を整理する

1. [unslop](../unslop/SKILL.md)を読み、文書の種類・構成・日本語をその手順で整える。日本語の規則をこのスキルで重複定義しない。
2. 読者が最後に答えられるべき問いを一文で決める。各節にも問いを一つ割り当て、結論、理由、図、制約の順を仮置きする。説明に必要な用語は初出で定義する。
3. 提供資料を事実の起点にする。実測、コードで確認した挙動、推定、提案、未確認を分ける。数値には単位・対象・条件・時点を付ける。時間の計測区間が不明なら「応答待ち」のような名前だけで定義を補わない。
4. 欠けている情報が結論を変えるときだけ尋ねる。配色や標準の図は自分で選ぶ。資料の言い換えだけなら外部調査は不要。新たに調べた事実には出典を付け、依頼者の資料を外部サービスへ送らない。

## 図を選ぶ

[図の選び方](references/figure-selection.md)を読み、読み手の問いから種類を選ぶ。図を一つ入れるたびに、その図で初めて分かることを決める。文章で十分なら図を増やさない。

- 順序と受け渡しは `flow`。
- 数値の大小は `bars`。
- 開始時刻、期間、重なりは `timeline`。
- 条件と選択肢の照合は `table`。

比較では同じ軸・単位・ラベル・色を使う。時間の合計と並列処理の経過時間を混ぜない。予測値を実測値と同じ確度で描かない。図の説明文で結論を示し、captionで出典・条件・限界を補う。

## HTMLを作る

### 標準の作り方

[入力仕様](references/input.md)と[入力例](assets/example.json)を読み、内容をJSONにする。[スキーマ](assets/document.schema.json)が受け付ける形だけを使う。例の文章・数値・出典は説明用なので、依頼の資料へ持ち込まない。

以下のパスはこのスキルのディレクトリからの相対パス。出力はユーザーの指定先、指定がなければ作業ディレクトリの `artifacts/<内容の名前>.html` とする。JSONも同じ場所に残す。

```sh
python3 scripts/render.py /absolute/path/document.json --output /absolute/path/document.html
```

このコマンドが配色・余白・軸・棒幅・数値ラベル・目次・テーマ切替を生成する。CSSとJSはHTMLへ埋め込まれるため、生成した1ファイルだけで読める。CDN、外部フォント、ビルド環境は要らない。入力の誤りは場所を示して拒否し、既存HTMLを変更しない。

### 標準の図で意味を表せないとき

枝分かれ、信頼境界、往復、入れ子の構造は、直列の `flow` に押し込まない。[図の選び方](references/figure-selection.md)のSVG手順を使う。標準レンダラーで紙面を作り、生成したHTMLの図を編集する。この場合は編集後のHTMLを正本とし、JSONから再生成すると特別な図が消えることを作業メモに残す。

[共通CSS](assets/style.css)のトークンを再利用する。本文の流れに必要な小見出し、強調、code、根拠リンク、補足のdetailsはHTMLに追加してよい。多くの節を一枚の巨大な図にまとめない。タブや動きは比較・順序の理解が改善するときだけ足し、印刷時とJS無効時にも情報を残す。

## 実物で確かめる

1. JSONと原資料を照合する。主体、条件、例外、数値、時点、確度が保持されているかを読む。レンダラーは出典の内容の正しさまでは判定しない。
2. ブラウザーで1440pxと390px、明暗両テーマを開き、図のラベル、矢印、caption、長い日本語、表を確認する。図中の文字を消したり、小さく縮めて収めたりしない。
3. Playwrightが使える環境なら[描画検査](scripts/check-render.cjs)を実行する。必要に応じて `NODE_PATH` をインストール済みモジュールのディレクトリに指定する。ブラウザー実行ファイルは `CHROME_PATH` で指定できる。

```sh
node scripts/check-render.cjs /absolute/path/document.html /absolute/path/render-evidence
```

4. 出力されたスクリーンショットを実際に開く。自動検査の成功だけで視認性を合格にしない。表の局所スクロールは許容するが、ページ全体の横はみ出しは直す。キーボード操作、リンク、印刷、JS無効時も確認する。検査の限界は[確認項目](references/verification.md)を読む。
5. 見つかった不備を直し、変えた図と表示条件を再確認する。実描画できない場合は未確認と報告し、見ていないものを「確認済み」にしない。

完成したHTMLを開き、リンクを返す。必要な場合だけ未確認の前提を短く伝える。初回生成で完成に近づける道具だが、初稿の無検査納品や、すべての入力での一発成功は約束しない。

## 設計の根拠

[参照スキルと採否](references/sources.md)に、調査時のスター数、固定版、採用した考え方、採用しなかった方針を記録している。通常の文書作成では読み直す必要はない。
