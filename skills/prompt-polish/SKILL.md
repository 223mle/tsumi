# prompt-polish — Opus 5.5 のエージェントに貼る依頼文を仕上げる

やりたいことのメモや書きかけのプロンプトを、ツールを使える Claude Opus 5.5 のセッション（Claude Code、Cowork など）に貼る1回分の依頼文に仕上げる。依頼文は日本語で書き、ファイル名・コマンド・識別子は原文のまま残す。

このスキルは依頼文を書くところまでを行う。依頼文に書いた作業そのものは始めない。

次の依頼は扱わない。

- システムプロンプト、エージェント定義、SKILL.md の作成や改善。[agent-design-review](../agent-design-review/SKILL.md) を使う。
- GPT や Gemini など、Claude 以外のモデルを名指しした依頼。
- プロンプトではない文章の清書。[unslop](../unslop/SKILL.md) を使う。

Opus 5.5 以外の Claude モデルを指定された場合は同じ手順で書き、Opus 5.5 向けの指針で書いたことを出力に一言添える。

## 進め方

1. **読めば分かる事実を先に調べる。** 依頼が指すリポジトリ、ファイル、会話、貼られた資料を読み、実在するパス、コマンド、テストの実行方法、データの場所を確かめる。確かめられなかった名前は依頼文に書かない。
2. **欠けている要素を洗い出す。** 次の節の表と照らす。
3. **答えで依頼文の構成が変わる点だけを聞く。** 聞くのは1問ずつ、最大3問とし、各質問に推奨の答えを添える。優先順は、目的の先にある成果、完了の判定手段、変えてよい範囲の順である。答えが違っても依頼文の構成が変わらない点は、聞かずに仮定を置く。欠けている点がなければ、聞かずに出力へ進む。
4. **範囲を変えずに深くする。** 「深くする4つの問い」に答え、依頼の範囲に収まる答えだけを依頼文に入れる。
5. **依頼文を書く。** 「書き方」に従う。
6. **照合してから出力する。** 「照合」の各項目を確かめ、「出力」の形で返す。

## 依頼文に入れる要素

依頼の大きさに合う要素だけを入れる。1ファイルの小さな修正に全要素を書くと、指示同士がぶつかり、読む側の判断の余地も奪う。

| 要素 | 書くこと |
| --- | --- |
| 成果と目的 | 作業名ではなく、終わったときに何が成り立っているか。その成果を誰が何に使うか。目的が分かると、書かれていない場面でも目的に沿って判断できる。 |
| 依頼者の現在地 | 何を知っていて、何を試したか。どこが不慣れか。指定しすぎると方向転換すべき場面でも指示に従い、曖昧すぎると一般的な定石で埋められる。現在地が分かれば、その間を取れる。 |
| 材料 | 加工前の材料の場所。ログ、データ、既存の実装、参考にするコード。要約や抜粋ではなく元の場所を指し、参考資料には何を見てほしいかを添える。 |
| 手法と道具 | その分野の一流の実務家が使う手法と道具。依頼者が知らなければ、何を使うかの選定から任せると書く。 |
| 完了の判定手段 | 通すテスト、実行するコマンドと期待する結果、照合するデータ。依頼者とモデルの感想以外で、結果の正しさを示すものを書く。 |
| 範囲 | 変えてよいものと、変えないもの。変えない理由も書く。 |
| 確認の線引き | 確認なしで進めてよい操作（ローカルで元に戻せるもの）と、先に聞く操作（削除、push、送信、共有の設定の変更）。 |
| 計画から外れたとき | 影響の小さい側を選び、記録して続ける。記録するファイルを指定する。 |
| 報告の形 | 終わったときに何を返すか。届かなかった目標があれば、その内訳も返させる。 |

## 深くする4つの問い

依頼文を書く前に、次の問いに自分で答える。大きくするのではなく、深くするための問いである。

1. 一流の実務家なら、頼まれていない何をするか。
2. 加工済みの資料の代わりに、どの生の材料から始めるか。
3. 具体的にどの手法と道具を使うか。
4. 依頼者と書き手以外の何が、結果の正しさを示すか。

依頼の範囲に収まる答えは依頼文に書く。範囲を広げる答えは、依頼文に入れずに「さらに引き上げるなら」へ回す。広げる案の作り方は[野心を上げる](references/ambition.md)にある。

## 書き方

Opus 5.5 は指示を文字どおりに読み、理由から一般化する。根拠と詳細は [Opus 5.5 の指針](references/opus-5-5.md)にある。

- してほしい動作を動詞で直接書く。「改善できますか」ではなく「変更してください」と書く。
- 指示には理由を添える。禁止だけを書くと、書かれた場面にしか効かない。
- 成果、制約、判定手段を書き、進め方は任せる。順序が結果を左右するときだけ、番号付きの手順にする。
- 強調のための語（「絶対に」「必ず」の連発、「重要:」の見出し）を使わない。効きすぎて、他の指示より優先される。
- 「最後にもう一度検証して」「慎重に考えて」という念押しを書かない。代わりに完了の判定手段を書く。
- 「あなたは一流の〜です」という役割の演技を頼まない。その職種が使う手法と道具を書く。
- 高い目標は、数値と、その数値が要る理由で書く。
- 互いにぶつかる指示を残さない。どちらを優先するかを書くか、片方を削る。
- 確かめたパスとコマンドは、そのまま書く。
- 文章を中心にし、見出しは増やさない。依頼文の体裁は、返ってくる出力の体裁に影響する。

文そのものは unslop の原則（働かない語を削る、指すものを推測させない、原文の条件を落とさない）で書く。完成例は[例](references/examples.md)にある。例は分量と配分を見るためのもので、型として写さない。

## 分からないことが多い依頼

3問で埋まらないほど欠けているときや、依頼者がその領域に不慣れなときは、質問を増やさない。依頼文の最初の段に、着手前にすることを書く。何を書くかは、欠けているものの種類で決める。対応は[分からないことの扱い](references/unknowns.md)にある。

## 出力

次の3つをこの順で返す。各技法の解説や、直した理由の説明は、求められたときだけ書く。

1. **完成版。** コードブロック1つに入れる。依頼文の中にコードブロックがあるときは、外側のフェンスをバッククォート4つにする。
2. **置いた仮定。** 確かめずに決めた点を箇条書きにする。依頼者が違うと気づいたら、どこを直せばよいかが分かるように書く。仮定がなければ省く。
3. **さらに引き上げるなら。** 依頼の範囲を広げる案を2〜3個、それぞれ1〜2行で書く。何が広がり、追加で何を渡す必要があるかを書く。選ばれたら、その案で依頼文を書き直す。

## 照合

- 元の依頼にあった対象、条件、数値、除外が、依頼文に残っているか。
- 依頼の範囲が広がっていないか。広げる内容は「さらに引き上げるなら」に移したか。
- 確かめていないパス、コマンド、事実を依頼文に書いていないか。確かめずに決めた点は「置いた仮定」に出したか。
- この依頼文だけを渡された、事情を知らない同僚が着手できるか。
- 完了の判定手段が、実行できる形で書かれているか。
- 強調のための語、念押し、役割の演技、ぶつかる指示が残っていないか。
- 小さな依頼に、要らない要素を足していないか。
