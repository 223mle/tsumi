# 例 — 分量と配分を見るための完成例

2つの例は架空のリポジトリと会社のものである。型として写さず、依頼の大きさに対してどの要素をどれだけ書くかを見る。例1は材料が手元にある依頼、例2は依頼者が不慣れで、分からないことが多い依頼である。

## 例1 — 材料が手元にある依頼

元の依頼は「このリポジトリのテストが遅いので速くして、というプロンプトを磨いて」である。

リポジトリを読んで、テストは `pnpm test` で動き、CI の `test` ジョブは `.github/workflows/test.yml` にあると確かめた。目標と、してはいけないことが分からなかったので、2問聞いた。答えは「CI を5分以内にしたい。今は14分」「テストを消すのは不可」だった。

完成版

```text
このリポジトリのテストの実行時間を短くしてください。CI の `test` ジョブが今は14分かかり、PR を出してからレビューを頼めるまでの待ち時間になっています。目標は5分以内です。

手を付ける前に、どこで時間を使っているかを実測してください。材料は、`pnpm test` を手元で走らせた結果と、`gh run list --workflow test.yml` で取れる直近20回分の CI のログです。一般論ではなく、遅いテストファイルの上位と、準備・並列度・入出力のどれが効いているかを数字で出してから、効果の大きい順に進めてください。

変えてよいのは、テストの設定、フィクスチャ、テストの補助コードです。テストの削除、スキップ、アサーションを弱める変更はしないでください。検査の範囲が狭まると、速くする目的と逆になるからです。製品コードを変える必要が出たら、変える前に理由を添えて聞いてください。

完了の条件は次の2つです。
- `pnpm test` が全件通り、テストの件数が着手前と同じである。
- 着手前と着手後の所要時間を、同じ計測方法で並べて示せる。

手元での編集と実行は、確認なしで進めてください。push と `.github/workflows/` の変更は、先に差分を見せてください。計画どおりに進まない箇所が出たら、影響の小さい側を選んで `notes/test-speedup.md` に記録し、作業は続けてください。

最後に、効いた変更を効果の大きい順に、変更前後の秒数と一緒に報告してください。5分に届かなかった場合は、残っている時間の内訳と、次に試す候補を書いてください。
```

置いた仮定

- 計測は CI の所要時間を基準にした。手元の実行時間を基準にするなら、目標の段と完了の条件を直す。
- 記録するファイルを `notes/test-speedup.md` にした。置き場所が決まっているなら差し替える。

さらに引き上げるなら

- **遅くならない状態を保つ。** 速くした後、CI に所要時間の上限の検査を足し、超えた PR を落とす。CI の設定を変える許可が要る。
- **待ち時間そのものを減らす。** 目的は PR の待ち時間なので、変更したファイルに関係するテストだけを先に回す構成を設計させる。テストと製品コードの依存関係を調べる作業が増える。

## 例2 — 依頼者が不慣れで、分からないことが多い依頼

元の依頼は「解約が増えた原因を調べてレポートにしたい。データ分析は詳しくない。プロンプトを作って」である。

データの場所を聞くと「`data/` に契約と利用ログの CSV がある」と答えがあった。レポートを読む人と、何をもって原因と言えるかは、依頼者も決めていなかった。質問を増やさず、着手前の段に回した。

完成版

```text
直近2四半期で解約が増えた原因を調べ、経営会議で打ち手を決める材料になるレポートを作ってください。

私はこのサービスの事業担当で、契約や利用の実態は知っていますが、データ分析には詳しくありません。そこで、分析を始める前に2つお願いします。まず、解約の原因分析で私が見落としていそうな点を教えてください。聞くべき問い、よい分析の姿、よくある誤りです。次に、分析の方針を左右する曖昧な点を、1問ずつ私に聞いてください。答えで方針が大きく変わる問いからお願いします。

材料は `data/` の CSV です。契約の一覧と利用ログがあります。集計済みの数字からではなく、行のデータから始めてください。最初に各ファイルの列、期間、欠損を確かめ、分析に使えない部分があれば知らせてください。

社内では「値上げが原因だ」と考えられています。この見方を前提にせず、データで再現できるかを試してください。再現できない場合は、ほかの説明を挙げ、それぞれがデータとどれだけ合うかを比べてください。使う手法は任せます。解約の分析を専門にする人が使う手法を選び、選んだ理由を書いてください。

原因と言える条件は、説明に使ったデータと別の期間でも、同じ傾向が出ることとします。出なかった説明は、仮説としてレポートに残してください。

`data/` のファイルは書き換えず、分析用のコードと中間ファイルは `analysis/` に置いてください。途中で方針を変えた箇所は、理由と一緒に `analysis/notes.md` に記録してください。

レポートは、最初に結論と確からしさを書き、次に根拠の図表、最後に急いで決めるべきことを3つ、賛否の論拠と一緒に並べてください。
```

置いた仮定

- 読み手を経営会議とした。現場の担当者向けなら、レポートの段を直す。
- 原因と言える条件を「別の期間でも同じ傾向が出る」とした。着手前の問答で変わることがある。
- 「値上げが原因」という社内の見方は、依頼者の発言から書いた。

さらに引き上げるなら

- **解約の兆しを早く見つける。** 原因の説明で終えず、解約の前に現れる最も早い兆候を探し、使っていない期間のデータで当たるかを確かめる。利用ログの期間が長いほどよい。
- **レポートをやめ、毎月回る仕組みにする。** 同じ分析を毎月自動で回し、変化があったときだけ知らせる。データを自動で取り出せる環境が要る。
