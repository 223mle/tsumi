# Opus 5.5 の指針 — 依頼文に関わる部分

Anthropic の公式ドキュメントから、エージェントに貼る1回分の依頼文に関わる点を抜き出した。システムプロンプトや API の設定だけに関わる点は省いている。出典は末尾にある。

## 指示は文字どおりに読まれる

- 頼まれたことをする。暗に期待されているだけのことはしない。「変更を提案できますか」と書くと提案だけが返る。編集してほしいなら「この関数を変更してください」と書く。
- 最小限より多くを求めるなら、そう書く。「ダッシュボードを作って」からは、機能の数や作り込みの水準を読み取らない。
- 出力の形式と制約は具体的に書く。順序や漏れのなさが要るときは、番号付きの手順にする。
- 事情を知らない同僚にこの依頼文を渡したら迷うかを考える。同僚が迷う依頼文では、モデルも迷う。

## 理由を添え、強調のための語を使わない

- 規則には理由を添える。「省略記号を使わない」より「読み上げソフトが読むので、省略記号は発音できない」のほうが効く。モデルは理由から、書かれていない場面にも一般化する。
- 大文字の CRITICAL や MUST のような強調は、新しいモデルでは効きすぎる。「このツールを必ず使え」は「〜のときにこのツールを使う」に弱める。
- 「迷ったら〜を使う」「既定で〜を使う」という一律の指示は、使いすぎを招く。使う条件を書く。

## 規則を並べず、判断の材料を渡す

- ぶつかる規則（「適切に文書を残す」と「コメントを足さない」）があると、モデルは衝突の解決に力を使う。規則の代わりに判断の基準を渡す。例は「周りのコードと同じ書き方にする。コメントの量、命名、慣用に合わせる」である。
- 手書きの細かい手順より、成果と制約を渡して考えさせるほうがよい。モデルの組み立てる手順は、人が指定する手順を上回ることが多い。
- 例は形式や文体を揃える手段として強い。その分、例に引きずられる。例を出すなら、用途に合う互いに違う例を複数出す。
- 単純な仕様より、中身のある参考資料が効く。HTML の試作、テスト一式、別のコードベースの実装、採点基準がこれに当たる。

## 検証と熟考の念押しを足さない

公式の指針は Opus 5 について、頼まれなくても自分の作業を検証するとし、以前のモデル向けに入れた「最後に検証して」という指示は検証のしすぎを招くので、書き直さずに削るよう勧めている。Opus 5.5 の手引きは、Opus 5 向けのプロンプトがそのまま使えるとしている。このスキルでは Opus 5.5 でも同じ扱いにする（ここは推論である）。

- 「慎重に考えて」「よく考えて」は足さない。Opus 5.5 は常に思考し、深さは effort の設定で決まる。チャットの試験では、この指示を外すと応答の開始が早くなり、品質の低下は見られなかった。
- 念押しの代わりに、正しさを示す手段を書く。通すテスト、実行するコマンド、照合するデータである。
- 同じ判断を何度もやり直させたくないときは、「方針を1つ選んで進め、前提を覆す新しい情報が出たときだけ見直す」と書く。

## エージェントの作業で書くこと

- **確認の線引き。** ローカルで元に戻せる操作（ファイルの編集、テストの実行）は自由に進めさせる。壊す操作、戻しにくい操作、共有のものに触れる操作（削除、force push、push、PR へのコメント、メッセージの送信、共有設定の変更）は先に聞かせる。
- **範囲。** 頼んだものだけを変えさせる。触れていないコードの整理、起こりえない場合のエラー処理、1回しか使わない補助関数は足させない。
- **テストの扱い。** テストは正しさを確かめるもので、解を決めるものではない。テストの値を埋め込む解や、テストを消す・弱める変更は認めないと書く。テストや課題のほうが誤っていそうなら、回避せずに知らせさせる。
- **読んでから答える。** 開いていないコードについて推測で述べさせない。
- **材料を広く探す。** 複数のアプリやファイルにまたがる作業では、依頼に出てこない場所にも必要な情報がある。着手前に関係しそうなものを広く開かせる。
- **長い作業の状態。** 構造のある状態（テストの合否）は JSON、経過のメモは文章、区切りは git のコミットで残させる。新しいセッションで続きから始めるときは、進捗ファイル、テスト、git log を読むところから始めさせる。
- **終わりの条件。** 人が見ていない長い作業では、文章だけの応答が出た時点で作業が残っていることがある。完了の条件とチェックリストを依頼文に書き、未完了の項目が残っていないかを確かめられるようにする。
- **サブエージェント。** 並列にできる独立した作業、文脈を分けたい作業に使わせる。単純な作業、順番に進む作業、1ファイルの作業は直接させる。Opus 5 系は必要以上に委譲しやすい。
- **後片付け。** 作業用のスクリプトやファイルを作ったら、最後に消させる。
- **報告。** 最初のツール呼び出しの前に何をするかを1行で述べさせ、最後に短いまとめを返させると、人が見ている作業で追いやすい。

調査の依頼では、成功の基準を定め、複数の情報源で裏を取らせる。込み入った調査では、競合する仮説を立てさせ、確からしさを記録させ、調査メモのファイルを持たせる。

## 材料の渡し方と体裁

- 長い資料（2万トークン以上）は依頼文の上に置き、頼みごとを最後に書く。
- 指示、背景、資料、例は、タグで区切ると混ざらない。タグの名前は揃える。
- 依頼文の体裁は出力の体裁に影響する。マークダウンの多い依頼文には、マークダウンの多い出力が返る。
- 形式は「〜しない」ではなく「〜する」で指定する。「マークダウンを使わない」より「文章の段落で書く」とする。
- 見た目を作る依頼では、「AI っぽい見た目を避ける」と書いても別の定型に替わるだけである。避けたい具体的な型を名指しする。

## 依頼文では変えられないもの

思考の深さ（effort）と出力の上限（`max_tokens`）は、セッションや API の設定で決まる。既定の effort は medium で、xhigh と max は品質の向上を測って確かめた作業だけに使うよう勧められている。依頼文で思考を増減させようとしない。
