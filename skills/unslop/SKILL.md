# unslop — 読み手が一度で理解できる日本語の文書を書く・直す

人が読む日本語の文書を、疲れた読み手でも一度で理解できるようにする。新しく書く（起草）ときも、依頼者の文章を直す（清書）ときも、同じ規則を使う。事実調査、設計の採否、承認・実装・検証の状態確認は扱わない。コミットメッセージ、チャットの返信、英語の文章も扱わない。

起草では、依頼に添えられたメモ・会話・コード・既存の文書を材料にする。以下で「原文」と書いた規則は、材料にも当てはめる。材料にない事実・理由・数値は作らない。

## どの規則よりも先に守る3つの原則

- **働かない語を削る。** 削っても意味が変わらない語は削る。「確認することができる」は「確認できる」とし、「〜という点に注意が必要です」は注意の中身だけを書く。
- **短く、普段使う語を選ぶ。** 「活用する」より「使う」、「実施する」より「する」を選ぶ。長い語は、その分だけ意味が正確になるときに使う。
- **規則に従うと文が悪くなるときは、別の直し方をするか、元のまま残す。** 規則をすべて守っても、機械が書いたように読める文は失敗である。

## 構成を決めてから書き、書いた本文を別に照合する

最初に、想定読者がこの文書で何を判断・操作するかを定める。材料を「現状・課題」「今回の決定」「制約」「会話中の個別例」に分け、各節へ配置する。その後に本文を書く。会話で了承されたことは採用理由の代わりにせず、個別例を製品の一般用途に広げない。

文書種別に必要な参照だけを読む。長い参照は分けて読み、出力が省略された場合は残りを読む。共通の判断は以下の本文に従い、説明量・節の役割に迷う場合は[構成](references/structure.md)と[完成例](references/worked-example.md)、ADR は[ADRの整理](references/adr.md)、PR は[PR説明](references/pr-description.md)を使う。

## 起草では、文書の種類と載せる事実を先に決める

清書だけの依頼では、この節を飛ばす。

1. [文書の種類](references/doc-types.md)を読み、チュートリアル・手順書・リファレンス・解説のどれにするかを決める。1つの文書には1つの種類だけを書き、混ざる場合は文書を分けてリンクする。PR説明とADRは種類を選ばず、次の節で挙げる参照に従う。
2. 載せる事実を選ぶ。何を載せるかを選ぶことも書き手の仕事である。読み手が判断や操作に使わない事実（作業の過程、どの変更でも同じ検証の記録）は載せない。材料にある条件・例外・制約は、種類に合う節に残す。
3. 決まったテンプレートがない文書では、見出しに節の要点を書く。「設定」ではなく「設定ファイルを先に置く」とする。作業の節は「開発用データベースを作り直す」のような動作で、概念の節は名詞で書く。テンプレートや社内の書式で見出しが決まっている場合は、その見出しを使う。

## 先に情報の置き場所と説明量を決める

**一文ずつ書く前に、構成を決める。** 清書で元の見出しや段落をそのまま引き継ぐと、説明の混在や書きすぎも残る。短い一文の依頼では構成の整理は不要。

次の判断を済ませてから本文を書く。途中の分類メモは出力しない。

| 決めること | 判断 |
| --- | --- |
| 各節で答える問い | 背景は現在の状態、課題は困りごと、提案・決定は変更内容。「今回も維持する」「対象外とする」は決定へ置く。選択肢を比較しないなら、採用方針の繰り返しではなく比較しない理由を示す。 |
| 説明の順序 | 対象や用途を紹介してから、例や条件ごとの動作へ進む。よくある場合を先に書き、例外は後に書く。結果・影響の節では、その節の結論を先に示す。 |
| 段落か箇条書きか | 後の文が前の文の理由・具体例・条件を説明するなら段落。独立した事実・変更点・制約なら箇条書き。読み手が順に行う操作なら番号付きリスト。同じ話題というだけで文章をつながない。 |
| どこで止めるか | 要点と必要な根拠・条件が伝われば止める。見出しや空欄を埋めるための説明は足さない。影響の小さい節は短いままでよい。 |

「変更しない」を小節ごとに繰り返している場合は、重複を除き、短い文章か箇条書きへまとめる。原文の事実を残すことと、見出しの数や説明の長さを残すことは違う。根拠のない「影響なし」、一般的なリスク・対策、求められていない検証計画を補わない。

## 決めた配置に沿って書く

[意味の保持](references/preservation.md)と[つながり](references/cohesion.md)、[語彙](references/vocabulary.md)を読む。文法の判断には[文](references/sentence.md)、飾りや過剰な修辞には[不自然な修辞](references/ai-smell.md)を参照する。

- 主体・動作と、それに付く条件・例外・数値・時点・不確実さを一組として移す。意味を左右する修飾語は、まず原文の表現を保つ。
- 原文にある因果・目的・対比だけを使う。「ため」「に伴い」「を受けて」などで、並列の事実に関係を付け加えない。理由が分からない場合も、接続詞で穴埋めしない。
- 同じ主体の連続する動作はまとめ、既に説明した対象を次の文で受ける。語尾や長さを変えるためだけに書き直さない。自然な原文はそのまま使う。
- 実在するファイル名・関数名・設定キー・コマンドは、コード書式でそのまま書く。言い換えや説明で代用しない。
- **対象を読者に推測させない。** 「これ」「それ」は指す名詞を、「など」は列挙の範囲を明確にする。例だけで全体が分からなければ確認先を示す。定義済みの専門語は残し、語が検出されたという理由だけで言い換えない。具体名や確認先が分からない場合は作らず、必要な情報を確認する。
- 一般論ではなく、この文書の対象に起きることを書く。「スキーマの変更で問題が起きうる」ではなく「列の名前を変えるとビルドが失敗する」と書く。原文に具体的な情報がなければ作らない。
- 清書では重複しない事実を残す。概要への短縮でも、独立した仕様・約束・実施条件を細部とみなして落とさない。特定情報を除く指示がある場合は従う。

文体は原文に合わせる。既存の文書に書き足す場合は、その文書の文体に合わせる。指定も原文もない場合は、です・ます調にする。

## 完成した本文を照合する

初稿をそのまま返さず、まず意味、次に構成を照合する。文書を保存した場合は、次のコマンドで曖昧な表現の候補を抽出する。パスはこのスキルのディレクトリを起点とする。

```sh
python3 scripts/find-ambiguous.py <文書のパス>
```

候補に付く問いに従い、指示対象・列挙の範囲・判断条件を文脈から特定できるか確認する。できなければ具体名・対応関係・確認先を補い、本文を直す。候補は誤検知を含むため、自動置換や単語の削除で済ませない。候補ゼロと形式チェックの成功は、次の照合の代わりにはならない。チャット内の草案も同じ観点で見直す。

1. 原文の各事実と、主体・条件・例外・数値・時点・確度が対応しているか。追加した関係表現には原文の根拠があるか。意味を変えずに直せない表現は原文へ戻す。
2. 起草した文書に、種類の違う内容が混ざっていないか。手順書に背景や設計の是非、リファレンスに指示や意見が入っていないか。
3. 各見出しの下の全段落が、その節の問いに答えているか。初出の対象を紹介する前に例外へ進んでいないか。別々の問いへの選択肢を同列にしていないか。文書の中で作った呼び名を、見出しや選択肢名を含めて、定義より前に使っていないか。コードの名前を言い換えていないか。
4. 各節の最初の文が、その節の結論や要点になっているか。テンプレートで項目が決まっている節でも、項目を並べる前に結論の文を置いているか。
5. 独立した情報を段落に詰めていないか。理由や連続する動作まで機械的に箇条書きへ分解していないか。
6. 同じ結論の反復、空欄を埋める一般論、不要な小見出しが残っていないか。削っても必要な事実・条件がすべて伝わる説明は削る。重大な制約を短さのために弱めない。

レビュー指摘を反映するときは、指摘された文だけでなく同じ種類の不備が文書の他の箇所にもないか照合する。この確認で見つかった箇所だけ直す。文章の良し悪しを文字数や変更箇所の数で判断しない。

## 出力

貼り付けられた文章の清書には、清書後の本文だけを返す。起草では、書いた文書の本文を返す。ファイルへの書き込みや修正を依頼された場合は対象ファイルを編集し、完了を簡潔に伝える。修正理由は求められたときにだけ説明する。

HTML比較ビュー、指摘レポート、採否の確認、A/Bテスト、別エージェントへのレビュー委譲は、このスキルの手順に含めない。

意味を一意に決められない箇所は推測で確定せず、原文の意味の幅を保つ。起草で必要な事実が材料にない場合は、作らずに空けておく。それでは文書が成立しない場合に限り、必要な点を短く尋ねる。
