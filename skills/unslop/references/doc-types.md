# 文書の種類 — 1つの文書で、読み手の1つの目的に応える

起草する前に、読み手がこの文書で何をしたいかを決める。種類は次の2つの問いで決まる。

- 読み手は手を動かしたいのか、理解したいのか。
- 読み手は学んでいる途中なのか、仕事で目的を果たそうとしているのか。

| | 学んでいる途中 | 仕事で目的を果たす |
| --- | --- | --- |
| 手を動かす | チュートリアル | 手順書 |
| 理解する | 解説 | リファレンス |

この問いは、文書全体にも、1つの節や1つの文にも当てはめられる。種類を混ぜず、分けてリンクする。手順書の中にリファレンスの表を置かない。リファレンスに手順の案内を入れない。手順書の中で設計の是非を論じない。

この4分類は [Diátaxis](https://diataxis.fr/) のもので、pstack の technical-writing を通して取り入れた。

## チュートリアル — 学ぶ人が手を動かして成功する

読み手が最後までたどり着けるかは、書き手の責任である。

- 冒頭で、何を作るかを書く。「〜を学びます」ではなく「〜を作ります」と書く。
- 各手順で目に見える結果を出し、何が見えるはずかを書く。出力、画面の変化、ログの行などである。結果は材料にあるものを使う。
- 説明は一言とリンクにとどめる。
- 「まず〜します。次に〜します。」のように、具体的な操作を順に書く。

## 手順書 — 目的を持つ人が作業を終える

読み手が抱えている課題を解く文書である。機械ができる操作の一覧ではない。

- 題は作業の名前にする。「データベースの初期化」ではなく「開発用データベースを作り直す」と書く。
- 読み手は作業に慣れていると考え、教えない。背景、経緯、網羅のための説明は入れず、必要ならリンクする。
- 操作は番号付きリストにし、1つの番号に1つの操作を書く。
- 操作は読み手を主体にして書く。「設定ファイルが作成されます」ではなく「設定ファイルを作ります」と書く。
- 条件や注意は、それがかかる操作の前に置く。「データを消す前に、バックアップを取ります」のように書く。
- 分岐は「〜したい場合は、〜します」と書く。
- 「簡単に」「すぐに」「〜するだけ」を手順に書かない。簡単なら、読み手はこの文書を開いていない。

## リファレンス — 調べる人が事実を確かめる

- 事実だけを書く。指示・説得・意見を入れない。
- 留保せずに言い切る。選択肢、既定値、上限、エラーを漏れなく書く。
- 説明する対象の構造に合わせて並べる。コマンドなら引数の順、設定ファイルならキーの順にする。コードと文書を行き来しやすくなる。
- コードから生成できるなら、生成する。

## 解説 — 理解したい人が「なぜ」を知る

- 1つの話題に絞り、製品を開かなくても読めるようにする。題の前に「〜について」を付けても通じるようにする。
- 実際にある「なぜ」の問いを軸にする。設計の判断、経緯、制約、ほかの案を書く。
- 書き手の評価を書いてよいのは解説だけである。案の長所と短所を並べるだけで終えず、どう評価したかを書く。評価の根拠が材料にない場合は作らない。

## 種類を1つに決めない文書

- PR説明とADRは、それぞれ[PR説明](pr-description.md)と[ADRの整理](adr.md)に従う。
- README は、種類の違う節の集まりであることが多い。導入は手順書、設定の一覧はリファレンス、設計の理由は解説として、節ごとに種類を決める。1つの節で種類を混ぜない。
- 設計書は解説として書くことが多い。決定事項と理由を残す記録なら、ADRの整理に従う。
