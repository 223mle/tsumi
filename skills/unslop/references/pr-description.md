# PR説明 — レビュアーが短時間で判断できるようにする

PR説明の読み手はレビュアーである。何のための変更か、何を確かめればよいかを、最初の数文でつかめるようにする。構成の一般的な判断は [structure.md](structure.md) に従い、ここではPR説明に固有の判断を扱う。

## 冒頭でイシューと解決策を示す

最初の2文で、何に困っていたか（イシュー）と、このPRで何をどう変えるか（解決策）を示す。イシューは1文に絞り、2文目で解決策を示す。原文で背景・方針・概要に分かれていても、この2文は冒頭に集める。実装の規則や処理の流れから書き始めない。

> 通知メールの送信時刻が利用者の時間帯に合わず、夜中に届くことがあった。このPRでは、送信時刻を利用者ごとの時間帯で決める。

## 挙動は例で示す

挙動の変化は、規則を文章で並べるより、出力例や変更前後の比較で示す。例は原文や実行結果にあるものを使い、作らない。原文の後ろにある例は、挙動を説明する位置へ移す。規則の細部は、レビュアーが判断に使うものだけを本文に残す。

## PR固有でない検証は書かない

CIでも実行するコマンドの成功やテストの件数のように、どのPRでも同じ検証の記録は書かない。書くのは、このPRのために行った確認と、確認できなかったことに限る。実行ログ、コミットの一覧、計測の表は本文に貼らず、置き場所へリンクする。

## レビュー依頼は問いの形にする

「レビューしてほしい点」に、決めた内容を事実として並べない。迷った選択肢、選んだ案とその理由、確認してほしいことを、問いの形で示す。

> 原文: キャッシュの有効期限を10分に固定します。設定で変えられるようにする案もありましたが、設定ごとの動作確認が必要になるため見送りました。
>
> 清書: キャッシュの有効期限を、設定で変えられるようにする案と10分に固定する案で迷い、固定にしました。変えられるようにすると、設定ごとの動作確認が必要になるためです。固定でよいか確認してください。

迷った案や理由が原文にない場合は作らない。理由が分からない項目は、確認してほしいことだけを問いにする。
