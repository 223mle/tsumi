# 語彙 — 対象と動作が分かる言葉を選ぶ

## 名前だけで理解できるかを判断する

用語の一般性は想定読者に照らして判断する。読者が知っている専門用語はそのまま使う。説明が必要な場合は、初出で何を指すかを短く示す。名称の直訳だけで分からないなら、対象・動作・用途を原文と提供された文脈の範囲で説明する。

- 主体や対象を広い分類名だけで表している場合は、読み手が特定できる名前や役割を添える。
- 識別子や数値には、何の値で、この説明にどう関係するかを示す。設定項目は、置く場所と用途を説明してから、省略時や例外の動作へ進む。
- 「一覧」「対象外」「既存」などは、何の一覧・範囲・時点かを読み取れるようにする。必要な参照先を示し、単に長い言葉へ置き換えない。
- 抽象的な動作や比喩には、何にどんな変化を加えるのかを示す。
- 操作の必要性が伝わらない場合は、原文にある目的を近くに置く。

すべての用語に定義や目的を付ける必要はない。読者が意味を取り違えたり、前の説明を探し直したりする箇所を直す。必要な情報がない場合は、名前や理由を創作しない。

## コードの名前をそのまま書く

コードベースが用語集である。実在するファイル名・関数名・設定キー・フラグ・コマンドは、コード書式でそのまま書く。「設定ファイル」「検査用のスクリプト」のような言い換えや説明で代用しない。読み手はその名前で検索し、コードと文書を行き来する。初めて出る箇所では、何をするものかを短く添える。名前が原文にない場合は作らない。

| 原文 | 清書例 |
| --- | --- |
| 予算の検査スクリプトを、書き込みモードで動かす | `budget.mjs --write` を実行する |
| 設定ファイルでログの置き場所を指定する | `app.yaml` の `log.dir` でログの置き場所を指定する |

## 比喩の名詞や造語で飾らない

開発者が声に出して言う言葉を使う。「土台」「レバー」「北極星」「ガードレール」「ラチェット」のような比喩の名詞は、技術用語のように見えても、多くの場合はもっと具体的な言い方がある。仕組みの名前か、何をするかで書く。例えば「ラチェット」は「減らすことしかできない上限」と書く。名前の付いた手法を使う場合は、初出で意味を示す。

## 文書の中で作った呼び名は初出で定義する

文書の中で作った呼び名は、読者が知らない。見出し・選択肢名・表を含め、最初に出る箇所かそれより前で定義する。定義より前の箇所では、呼び名を使わずに内容で書く。採用した選択肢の名前に呼び名が入っている場合は、選択肢名を内容で言い換えるか、先に定義を置く。

定義は、誰が何をした結果のものか、いつ作られるかで書く。呼び名と同じ語で説明を一周させない。

| 原文 | 清書例 |
| --- | --- |
| **案B（承認済み版と比べる）を採用する。** 承認済み版: 最後に承認した時点の版 | 管理者が内容を確認して承認ボタンを押すと、その時点の文書のコピーを保存する。以下、このコピーを承認済み版と呼ぶ。**案B（前回の承認以降の変更を比べる）を採用する。** |

## 書き換え例

以下は文脈から対象や意味が分かっている場合の例であり、特定の語を禁止する一覧ではない。

| 原文 | 清書例 |
| --- | --- |
| スクリプトが処理する | 請求書の生成スクリプトが、受注データからPDFを作成する |
| 調査基準は `abc1234` | この説明は、対象リポジトリのコミット `abc1234` のソースコードを確認して記載した |
| 誤った拒否が発生する | 本来は許可すべきリクエストを、システムが誤って拒否する |
| 設定を凍結する | 設定ファイルへの書き込みを禁止する |

## 指すものを見失わせない

「これ」「それ」は、読み手が対象を探し戻らなくて済むよう「この API」「保存したレポート」のように名詞を添える。直前の名詞を一意に受け、読み違いも読み戻りも生じない省略は残してよい。

同じ対象は同じ名前で呼ぶ。語彙を変えるためだけに同義語を混ぜない。専門用語と説明の順序は、読者に伝わりやすいほうを選ぶ。原語の併記は検索や後続の説明に必要な場合に限る。

## 読み手が対象を特定できない抽象語を残さない

語の出現だけで曖昧と判定しない。初版の復元テストに従い、読み手が「誰が・何を・どうする」を文脈から具体的に思い浮かべられるかで判断する。指示語・列挙・判断条件を省略し、読み手に「具体的には何か」を推測させた表現は残さない。

定義済みの専門語や、読者が知っている一般用語は残す。例えば「ホストと実行環境から参照する同じファイルを共有ファイルと呼ぶ」と定義した後の「共有ファイル」は問題ない。逆に、指すファイルの説明がなければ補う。特定の分野で使う名詞を、一律の検出・禁止対象にしない。

- 「など」は削除して列挙し切るか、対象範囲を示す。例として挙げる場合は例と明記し、全体の列挙と区別する。
- 対象が増える一覧は全文を写さず、代表例と管理元のファイル・一覧へのリンクを示す。
- 複数の意味がある語には用途を添える。「接続先」なら、どのサービスに何のために接続するかを書く。
- 操作の結果は、読み手が見える場所や物の変化で書く。「共有される」なら、どの場所とどの場所が同じデータを見るかを示す。

「適切に」「大幅に」も、判断条件や変化量を材料から特定する。具体名・数値・リンクが材料にない場合は創作しない。原文の対象範囲を保ち、必要なら確認する。既に定義した対象を短く受ける表現まで機械的に展開しない。

対比する概念は、同じ観点・粒度の言葉で表す。ただし、語の対称性を整えるために条件や意味の違いを消さない。
