# 情報の配置から完成文までの例

個々の文を自然にする前に、情報の役割を分ける。次の例は、何を残し、何を変えるかを示すためのもの。文書ごとに同じ見出しや段落数を使う必要はない。清書の例を2つ示した後に、メモから起草する例を示す。

## 依頼と原文

依頼: 次の企画書を、内容を変えずに清書する。

> 課題：読書会の案内は、運営担当者が会員ごとに送っている。案内は毎月送っている。会員は開催日を知りたいとき、以前の案内を探している。新しい会員が増えている。運営担当者の人数は変わっていない。開催日を一か所で確認できるようにしたい。運営担当者が予定表を公開する。閲覧を希望した会員だけに予定表のURLを送る。会員は予定表を開く。開催日を確認する。閲覧を希望しない会員には従来の案内を続ける。運営担当者は変更があった月だけ予定表を更新する。URLを許可なく第三者に渡してはならない。

## 先に決める配置

- 現在の案内方法、会員が日程を探す動作、会員数と担当者数は背景。
- 開催日を一か所で確認できるようにしたい、という望む状態は目的。
- 予定表を公開しURLを送る、閲覧する、更新する、という方法は提案。
- 希望者だけに送ること、希望しない会員への従来対応、更新する月、URLの扱いは、該当する方法と一緒に残す。

会員数と担当者数が並んでいるが、それが日程を探す負担の原因とは原文に書かれていない。「会員が増えたため」と結ばない。理由を補わなくても背景として記載できる。

## 清書後

### 背景

- 運営担当者は毎月、会員ごとに読書会の案内を送っている。
- 会員は開催日を知りたいとき、以前の案内を探している。
- 新しい会員が増えている。
- 運営担当者の人数は変わっていない。

### 目的

会員が開催日を一か所で確認できるようにしたい。

### 提案

運営担当者が予定表を公開し、閲覧を希望した会員だけにURLを送る。会員は予定表を開いて開催日を確認する。閲覧を希望しない会員には、従来の案内を続ける。

運用上の条件は次のとおりとする。

- 運営担当者は、変更があった月だけ予定表を更新する。
- URLを許可なく第三者に渡してはならない。

## この修正で行ったこと

「案内を送る」「毎月送る」は一文にまとめた。原文にある主体と動作が同じなので、意味を加えずにまとめられる。「予定表を開く」「開催日を確認する」も同じ会員の動作としてつないだ。

「課題」という原文の見出しの下に方法まで並んでいたため、背景、目的、提案に分けた。目的の節には、予定表を公開するという手段を置いていない。提案の節では、一つの方法を説明する動作とその条件を一緒に扱った。

「希望した会員だけ」「変更があった月だけ」を残した。「許可なく第三者に渡してはならない」もそのまま残した。これを「第三者に渡してはならない」にすると、許可を得た場合まで禁止することになる。否定文を簡単にしても、禁止の範囲を広げてはいけない。

背景の独立した事実と運用上の条件は箇条書きにした。前の文を受けて理解が進む動作の説明は、段落として残した。

文章がもともと明確な部分は、そのまま使った。文末を毎回違う形にしたり、すべてを長い一文につないだりする必要はない。

## 影響が小さい節を短くする例

原文:

> 変更するのは一覧画面の並び順だけである。影響は表示に限られる。
>
> ### 保存内容
> 保存内容は変えない。保存内容への影響はない。
>
> ### 権限
> 権限を変えないため、閲覧できる利用者は変わらない。
>
> ### まとめ
> 変更は表示だけである。保存内容も権限も変えない。

清書:

> 変更は一覧画面の並び順に限られる。保存内容と権限は変えず、閲覧できる利用者も変わらない。

変更範囲と、その説明に必要な事実を残し、同じ結論の反復と不要な小見出しを除いた。ここに一般的なリスクや確認手順を補って欄を埋めない。短い節のままで説明が完了している。

## メモから手順書を起草する例

依頼: 次のメモから、開発者向けの手順書を書く。

> `make db-reset` で開発用 DB を消して作り直す。消えるのは手元の DB だけ。作り直したあと `make seed` で見本データを入れる。Docker が動いていないと失敗する。ステージングでは使えない（`APP_ENV=staging` だと止まる）。前は手で SQL を流していたが、手順が人によって違ったので make にまとめた。

### 先に決めること

- 読み手は作業を終えたいので、種類は手順書にする。
- 「前は手で SQL を流していた」という経緯は、作業に使わないので載せない。残す必要があれば、解説かPR説明に書く。
- 消える範囲とステージングで使えないことは、操作の前に読むべき条件なので、手順より前に置く。
- Docker の条件は、それがかかる操作の前に置く。

### 起草後

> ### 開発用データベースを作り直す
>
> 手元の開発用データベースを消して作り直し、見本データを入れます。消えるのは手元のデータベースだけです。ステージング環境では使えません（`APP_ENV=staging` のときは止まります）。
>
> 1. Docker を起動します。Docker が動いていないと、次の手順が失敗します。
> 2. `make db-reset` を実行して、データベースを消して作り直します。
> 3. `make seed` を実行して、見本データを入れます。

### この起草で行ったこと

見出しは、読み手が終えたい作業の名前にした。コマンドと環境変数は、メモの名前をそのままコード書式で書いた。1つの番号に1つの操作を書いた。メモにない「成功すると〜と表示される」という確認や、作り直す理由は足していない。完了の確かめ方を書くには、その出力が材料に必要である。
